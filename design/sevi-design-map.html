Version 0 · design review

Sevi turns blog links into audio you can question by voice

You send a link in Telegram and get the blog back as one audio file. You reply to any message with a voice note or text to ask about it, and the answer comes back as a voice note or as text. It runs on your machine for one person. This page draws the mechanism behind each part, then lists the choices worth arguing with.

The whole thing

The whole design on one page

A link or a question comes in through an adapter, passes one door that checks a signed token, and reaches a Core that decides, costs and remembers. Everything below is drawn in more detail further down.

The shape

Everything crosses one HTTP line

Chat apps are thin adapters. They know their own platform and nothing else. The Core holds every rule and talks to the outside services. That one line is what lets a Discord adapter or a web page be added without touching the Core.

Adapters use HTTP even when they share a process

A Discord adapter or the web page can be written in any language, run anywhere, and cannot reach into Core internals.

Voice notes travel as base64 inside JSON, and every message pays a localhost hop that a function call would not.

Is a pluggable adapter layer worth that for a one-person tool, or should the adapter call Core directly until a second adapter exists?

The Core knows no platform

Threading, voice, text and cost rules are written once. An adapter only turns "a reply to message 13" into a handle Core understands.

Anything platform-specific that users like (buttons, edit-in-place status) has to be expressed as generic events and rebuilt in each adapter.

Are the event kinds (progress, confirm, error, cost, done) enough for a web page, or will it want something richer?

Journey one

A link becomes one audio file, and money is asked for first

Every step that can be skipped is skipped: a link already voiced costs nothing, the page text is cached, and anything the price book estimates above $0.20 waits for a Yes.

One stitched MP3 per blog

One file is one thing to play, seek and reply to. You asked for it.

A very long blog is one big upload. Telegram caps bot uploads at 50 MB, which is hours of audio at this bitrate, so it is far away but real.

Would chapters or parts be better for a two-hour read, so a reply can point at a part?

Page text and audio are cached forever

Re-sharing a link costs $0.00 and is instant. The audio cache is keyed by link, speech model and voice.

A blog that is edited later is not noticed. Changing the voice or speech model re-speaks every blog on first use.

Should cached text expire, or should there be a "refresh" you can ask for from Telegram?

Several blogs at once, each side by side

Every message is its own job. In a test, three blogs shared together all finished speaking after 0.62 s, where one after another would take 1.8 s. The same link sent twice at once is spoken once: the second waits, then reuses it at $0.00.

Jobs share one OpenRouter account, so many at once can hit its rate limit, and nothing caps how many run together. Chunks within one blog are spoken in order.

Should the number of blogs made at the same time be capped?

Ask before spending over $0.20

Cost stays visible and under your control. The threshold is a config value.

A prompt interrupts. Anything just under the line runs unattended.

Is a fixed dollar line right, or should it be per-day budget so many small blogs also stop?

Journey two

Replies point at a message; the model reads the whole blog's conversation

Which message you reply to only decides which blog the question belongs to and what "that" means. The model is always given everything said so far about that blog, in time order.

Whole session in context, no branches

A question asked from an old message still sees everything said since. The model can say "as I explained earlier" truthfully.

Every turn re-sends the blog and the whole history. Providers cache the repeated prefix (billed at a tenth), and the Gemini lite window is about 1M tokens. A conversation past about 25,000 tokens is summarised (next card).

Is the full timeline right until a chat gets long, or do you also want a command to start fresh on one blog?

Long chats are summarised by size alone

Over 100,000 characters (about 25,000 tokens), the oldest messages fold into a stored summary until half that remains in full; the newest message is never folded. The summary lists your questions in order, in your words. Setting 0 turns it off.

A summary loses detail; the first version blurred a first question until the prompt was tightened. It costs one extra cheap call (about $0.0005). The blog itself is never summarised.

Is 25,000 tokens the right size, and would you want to read the summary?

A reply to an unknown message is refused

Answering without the blog invented "deep work" once. Now Sevi says it does not remember the message and tells you to resend the link.

Replies to audio sent before threads existed fail until the link is resent (free, thanks to the cache).

Would it be better to guess from the chat's last blog than to refuse?

A message that replies to nothing starts a new chat

Nothing attaches to an old thread by accident. The model is told it has no document.

You cannot "just carry on" without tapping reply.

Is tapping reply on every follow-up acceptable on a phone, many times a day?

Journey two, one step

One model call hears you, writes the answer and decides how to deliver it

A voice note goes to the model as audio. It returns a transcript, the answer and a format in one JSON object, so the transcript is stored without a separate transcription call.

Transcript, answer and format in one call

One round trip, one bill, and the model uses the real audio (tone, language) to decide.

The model must follow a JSON contract. With the 3.5 model one "answer as text" was carried forward to later turns; the prompt now says a request applies to that turn only.

Are you comfortable with the model, not a rule, deciding voice versus text?

A voice note reply, not an audio file

It looks like a conversation: waveform bubble, inline playback, Telegram's own speed button. The blog stays an audio file with a seek bar.

No title and no seek bar on answers; long answers are awkward to scrub.

Fine for 30-60 second answers; is it still right if you ask for long explanations?

Chat model is plain config

Tested: a 3.8 model needed only the model line. A model that cannot hear audio needs models.stt set.

Speech models other than Gemini's are untested. Sample rate, tokens per second and voice names are assumed.

Do you expect to swap the speech model, or only the chat model?

Money

Cost is arithmetic on a stored price, checked once a week

No provider is asked what a call cost. Tokens come from the response (or from audio length), the price comes from SQLite, and the stored price is refetched when it is older than seven days.

Compute, do not look up

The provider's charge record can take a minute to appear; computing it makes the cost known the moment the audio is, so the cost is in the caption.

Speech tokens are derived (25 per second, observed), so a model with a different billing unit would be wrong until checked. Prices come from OpenRouter's list only.

Is a weekly self-check enough, or should every Nth call be reconciled?

Failed attempts are not billed in the ledger

A retried 429 produces one ledger row, from the attempt that worked.

If a provider bills a failed attempt, the ledger undercounts. Not seen so far.

Do you want the OpenRouter account balance shown beside the ledger total as a cross-check?

Storage

Eight tables; the messages table is the conversation

Everything the model needs is rebuilt from rows: the timeline from messages, the blog from page_cache, the money from ledger. SQL lives in files and is compiled to typed Go by sqlc.

SQLite through sqlc, UUID text ids, audit columns

One file, no server, typed queries, and ids that can be merged across machines later. Audit columns are ready for accounts.

The driver needs cgo (a C compiler) to build. Migration 004 rebuilt a table and silently dropped old thread mappings once.

Should real-data migrations be required to convert rows rather than drop tables from now on?

Audio on disk, referenced by key

The database stays small. The blob interface can point at object storage later.

Disk files have no cleanup. Your own voice notes are stored too.

How long should voice notes and old audio be kept?

Next step

The design leans on a machine, and Workers is not one

Each row is something version 0 assumes and what it turns into on Cloudflare. Read the red rows first: they decide whether the Core is rewritten or moved as it is.

The first decision is where the Core runs

Everything else follows from it. Keep Go (a container that also has ffmpeg), or rewrite the Core in TypeScript for native Workers.

Keeping Go keeps the tested pipeline but not the free tier. A rewrite is large, and ffmpeg still has no home in a Worker.

Is "near free" the goal, or "runs without my laptop being on"? They point at different answers.

Adapters over HTTP help here

Only the Telegram adapter changes (polling to webhook). The Core's API and the clients are untouched.

The Telegram webhook endpoint becomes public, so it needs Telegram's secret-header check on top of the signed token our adapter already sends.

Do you want the Core callable from outside, or only through the Telegram webhook?

Where I would push first

The choices most likely to be wrong

Ordered by how much it would hurt to find out late. Each one is a decision, not a bug; the app works as built.

1. Jobs live in memory

Simple, and enough for one person.

A restart drops a job that was running; the poller shows nothing. Sessions and costs survive.

Is losing an in-flight 3-minute job on restart acceptable, or must jobs be resumable?

2. Adapters prove themselves with a signed token

Adapters share one secret and mint a five-minute JWT per call. Anything else gets a plain 401; Core will not start without secrets or on an address other machines can reach.

A browser cannot hold a secret, so a web page needs a login step that issues tokens. On Cloudflare the Telegram webhook needs a second check: Telegram's secret header.

When the web page exists, what should it log in with?

3. OpenRouter is assumed everywhere

One key, many models, one public price list.

Speech endpoint, price list and weekly check are OpenRouter-shaped. A direct Google or OpenAI key needs per-provider adapters.

Will you ever use a direct key? That decides if this is worth generalising now.

4. One model decides voice versus text

Works in any language and phrasing.

It misjudged once. A model change could change the behaviour.

Do you want a simple override, such as a "/text" prefix, in addition?

5. Attachments are silently ignored

Moved to version 1 on purpose.

A document sent to the bot gets no reply, which looks like a crash.

What types matter first: PDF, images, pasted text files?

6. A single upstream model rate-limits

Retries handle short bursts.

A limit longer than about 45 seconds still fails the question. A fallback model would cover it.

Is a pricier fallback model, used only on failure, worth configuring?

7. ffmpeg and a C compiler are hard requirements

Best audio quality for the least code.

Both complicate any hosted deployment.

If hosting forced a choice, would you give up Opus voice notes for a simpler path?

8. One user, one allowlist

Keeps cost and abuse simple.

The audit columns and per-session ledger would need accounts to share this.

Is anyone else ever meant to use it, even one friend?

Parked on purpose

What was moved to later, and why each is doubtful

Version 0 stops at what you listened to and used. Each item below was moved out deliberately. The last line of every card says what can go wrong while it waits.

Version 1

Attachments: documents and images

The listen-and-ask loop was the goal; files are an extra input.

Telegram ignores a document with no reply, which looks like a crash. Sending a file is the first thing a new user will try.

Doubtful while it waits: it is silent. A one-line "I can't read files yet" was not added.

Hardening

Error wording per failure class, a clean shutdown, backfilling calls whose price was unknown, a log review.

A restart drops a job that is running; a blocked page, an out-of-credit account and a missing ffmpeg all get generic wording.

Doubtful while it waits: a stuck or half-finished job has no recovery.

Jobs that survive a restart

Sessions and costs already persist; only the running job does not.

Restarting during a 3-minute blog loses it and the status message stops moving.

Doubtful if you restart the server often, or redeploy while something is running.

Fallback model

Retries cover short rate-limit bursts. A second model costs more and changes who answers you.

A limit that outlasts about 45 seconds of retries still fails the question.

Doubtful on busy provider days; it happened twice in a few hours of testing.

Gemini voice settings

You asked to review this later: a different voice for answers, a speaking-style instruction.

One voice (Kore) for everything. OpenRouter does not list which speech settings a model accepts, so each setting needs trying.

Doubtful: it is unknown which settings actually take effect.

Web page and Discord adapter

One adapter is enough to use it; a second would prove the contract.

Only Telegram has ever used the API, so assumptions that only a second adapter would expose are untested. A browser cannot hold the shared secret, so the web page needs a login step.

Doubtful: the "pluggable" claim is unproven until a second adapter works.

Direct provider keys (not OpenRouter)

One key and one price list are simpler.

The speech endpoint, price list and weekly price check are OpenRouter-shaped. A direct Google or OpenAI key needs per-provider adapters.

Doubtful if you ever want to avoid OpenRouter's margin or its upstream limits.

Playback speed, blog description, multi-user keys

Nice to have: faster audio (ffmpeg, no extra speech cost), a one-line summary under the audio, other people bringing their own key.

Audio is at normal speed; the caption is title, length and cost; there is one user.

Not doubtful, only unbuilt.

Raised in the review, not scheduled

Page text that never expires; a blog split into parts; a per-day budget; how long voice notes are kept; a "/text" override.

An edited blog is not noticed; a very long blog is one big file; many small blogs below $0.20 each are never questioned.

Doubtful: each needs your decision before it can be built.

Version 2

Other voice vendors, ElevenLabs first

Swapping between Gemini speech models is already one config line; another vendor is a new adapter.

Its own endpoint, voice names, audio format and sample rate, and billing unit (not Gemini's 25 tokens a second). The price list, the estimate and the weekly check each need the same treatment.

Doubtful: the audio code assumes 24 kHz raw audio from Gemini.
